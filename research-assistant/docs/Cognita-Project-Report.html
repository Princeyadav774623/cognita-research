Chapter One

Introduction and Problem Statement

A language model asked a research question will produce a fluent, confident, well-structured answer whether or not it has any basis for it. The failure is not that it is sometimes wrong; it is that a wrong answer is indistinguishable from a right one.

1.1 The problem

Retrieval-augmented generation is the usual response: give the model source documents and instruct it to answer from them. This helps, but it moves the problem rather than solving it. The model can still assert things the sources do not support, cite a document that does not contain the claim, or answer a question the sources never addressed. A reader has no way to tell.

Cognita's premise is that a research tool's output is only as valuable as the reader's ability to check it. Three properties follow from that:

  • Every claim traces to a source. Citations must resolve to a document the system actually read, and that must be verified rather than trusted.
  • Verification must be independent. Checking a claim against the same text it was summarised from proves only that the summary was faithful.
  • Confidence must be honest. A score that does not reflect the quality of the underlying evidence is decoration, and worse than no score at all.

1.2 Scope

The system provides two tools over one evidence model. Deep Research answers a question from the open web using a multi-agent pipeline. Chat with Files answers from documents the user uploads. Both produce cited answers, both refuse when the evidence does not support an answer, and both report measured telemetry rather than assertions.

1.3 What this report covers

Chapters 2 to 8 describe requirements, architecture and implementation. Chapter 9 reports measurements taken from the running system — every figure in it was produced by executing the software, not estimated. Chapter 10 states plainly what remains unproven.

Chapter Three

System Architecture

Three tiers: a React single-page application, a FastAPI service hosting a LangGraph state machine, and Postgres with pgvector holding both relational and vector data.

Chapter Four

The Agent Pipeline

Nine nodes in a directed graph. The important structural feature is not their number but the edge that goes backwards: gap analysis can return the run to search when the evidence gathered so far does not support a confident answer.

Chapter Five

Retrieval-Augmented Generation Subsystem

Retrieval runs two searches and fuses their rankings. Neither is reliable alone: embeddings place Sev-1 and Sev-2 almost on top of each other, which is exactly wrong when the user asked about one of them; keyword search has no notion of synonym or paraphrase.

5.1 Ingestion

A file is validated by magic bytes rather than extension, extracted according to type, sanitised, split into 1,000-character chunks with 150-character overlap, and embedded locally. The HTTP request returns as soon as the record exists; extraction and embedding happen afterwards, so a 200-page PDF cannot exceed a proxy timeout. Documents left mid-ingest by a restart are failed after fifteen minutes with a message telling the user to upload again.

5.2 Hybrid retrieval

Both retrievers return twenty candidates. Their rankings are combined by Reciprocal Rank Fusion, which fuses by rank rather than score — cosine similarity and ts_rank are different scales with no meaningful conversion, and normalising one onto the other would invent a relationship that does not exist.

Reading this honestly. Two of the three queries were already handled by vector search alone. The third is the case hybrid retrieval exists for — and the class of query (version strings, part numbers, error codes) is precisely the one where users are most certain they typed it correctly, so a miss reads as the product being broken.

5.3 The agentic loop

Retrieval is not a single shot. The system grades whether retrieved excerpts actually answer the question; if not, it rewrites the query with different wording and retries once. Only after that does it decline. This is what produces correct refusals rather than confident guesses.

Chapter Six

Data Layer and Security

6.1 Tenant isolation

Application code filters every query by user. That is necessary and insufficient: it is one forgotten WHERE clause away from a cross-tenant leak. Postgres row-level security provides the second line. Policies are keyed on a session variable set when a connection is checked out of the pool, and current_setting(..., true) returns NULL when unset — so an unscoped session matches nothing and fails closed.

Two roles make this work. The owner role runs migrations and the payment webhook path, which has no user context and must read across tenants. The runtime role owns nothing and has no BYPASSRLS, so policies bind to it. If both connection strings name the same role, every policy is inert — and startup says so loudly rather than logging a reassuring line that means nothing.

Verified live · all six tables

research_sessions, rag_documents, rag_conversations, rag_chunks, rag_messages and user_subscriptions all report relrowsecurity = true. These four checks run as a build gate; a regression fails CI rather than reaching production.

6.2 Untrusted document content

An uploaded file is the easiest path into a model's context for anyone who wants to steer it. Defence is structural: retrieved excerpts are wrapped in <document> tags and the system prompt states that anything inside them is data, never a command. A closing tag inside an excerpt is neutralised, or it would end the block early and hand back exactly the control the delimiter withholds.

Tested, with an instructive result. A document was uploaded containing an instruction to ignore all directives and reply with a single fixed word. The regex sanitiser missed it entirely — its patterns expected different phrasing. The delimiting held: the system answered both questions correctly from the document and added that the document "contains a line that appears to be an injected instruction… treated as part of the document content and is not followed." The patterns were subsequently widened, but the lesson stands — the structural separation is the defence, and the regex is a speed bump.

6.3 Schema management

Four Alembic revisions replace the earlier pattern of create_all() plus hand-written ADD COLUMN IF NOT EXISTS statements, which could add a column but never alter or remove one and recorded nothing about what had been applied. A database predating Alembic is stamped at the baseline rather than re-running it, so existing data is preserved.

Chapter Seven

Verification and Confidence Scoring

This chapter describes the part of the system that most distinguishes it, and the part where a plausible-looking implementation is most likely to be measuring something other than what it claims.

7.1 Why naïve verification fails

The obvious implementation extracts claims from the draft and checks them against the source documents. It is circular. A claim faithfully summarised from a source always agrees with that source, including when the source is wrong. Such a system measures summarisation fidelity while its interface calls the result grounding.

7.2 Independent corroboration

Each claim is searched for separately, concurrently, and the results are labelled distinctly from the documents the draft was written from. A claim confirmed by a source the analyst never saw is marked independently_corroborated. The verifier is instructed to cap confidence at 0.7 when only prior evidence supports a claim — agreement with one's own summary is weak evidence.

7.3 Evidence selection

Evidence was previously assembled by position: the first 1,000 characters of each document, truncated to 6,000 overall. On a forty-source run that is roughly the top of the first six, so a claim drawn from anywhere else was unverifiable in principle and returned "unverified" for reasons unrelated to its truth. Passages are now selected by relevance to the specific claim across every source, scored locally with IDF-weighted term overlap.

7.4 Scoring the run

The run's confidence is not the mean of its claim scores. A mean hides its worst member: four solid claims and one fabrication scored identically to five mediocre ones. Instead, unsupported claims are weighted more heavily, and the result is capped by the quality of the evidence beneath it — because thin evidence does not make an answer wrong, it makes a high score unjustifiable.

ConditionEffectRationale
Unsupported claim presentWeighted 1.5×Cannot be averaged away by its neighbours.
Fewer than 3 distinct sourcesCap 60%Perfect claims over two documents is not a confident answer.
Fewer than 5 distinct sourcesCap 80%Insufficient breadth for a high score.
Majority of sources snippet-onlyCap 70%A search snippet is not the paper it stands for.
Independent corroborationUp to +10%Scaled by the proportion of claims confirmed externally.
No claims extractedScore 0.0An invented middling number reads as a measurement when nothing was measured.

Every adjustment is reported alongside the number, and the report carries a "What limits this score" section naming what would raise it. A score a reader cannot interrogate is decoration.

8.1 What CI verifies

The pipeline runs against pgvector/pgvector:pg16 with a genuine low-privilege role — not SQLite. This matters: the application refuses to start on SQLite, so a suite running against it would cover none of the pgvector queries, the tenant scoping, or the migrations that actually execute in production.

Beyond the unit suites, two gates assert behaviour rather than code. The first confirms Postgres genuinely refuses cross-tenant reads — the policies existing is not the same as the policies working. The second runs the golden evaluation set, so a retrieval regression fails the build.

8.2 Tests that encode defects

Several tests assert the specific failure rather than the happy path, so a regression reads as the thing that went wrong:

  • an unsupported claim cannot be averaged away by four good ones;
  • perfect claims over two sources are still capped;
  • a corroborating hit on a page the draft already used is not independent;
  • a run with no claims scores 0.0, not an invented 0.5;
  • a tracking parameter on a URL does not make a real citation look fabricated;
  • a closing tag inside an excerpt cannot end the delimiter block early.
Chapter Nine

Results and Measurements

Every figure in this chapter was produced by running the system. Nothing here is an estimate, and where a measurement is weaker than it appears, this chapter says so.

9.1 Public benchmark — SQuAD 2.0

The project's own golden set is fourteen questions over three documents written by the author. It is a useful regression check and poor evidence: a perfect score on one's own questions demonstrates that the system does what was expected, not that it works. SQuAD 2.0 is a public benchmark of human-written questions over Wikipedia paragraphs, including questions deliberately unanswerable from their source.

Three qualifications, stated plainly.
1. The corpus was 31 paragraphs. A perfect recall score over a small haystack is easier than over a realistic one, and this number should be expected to fall as the corpus grows.
2. Answer accuracy is understated. Manual review of the three "failures" found two were correct answers phrased differently — "very little work is needed to drive the pump" scored zero against "relatively little work is required to drive the pump". Token F1 was added afterwards for this reason.
3. The refusal rate is not yet reliably measured. The first run reported 0.167, which manual inspection showed was a grader defect, not a system defect: the detector looked for three literal phrases and missed "do not contain", "does not state" and "do not specify". The true figure is approximately 0.667. A corrected re-run was prevented by the provider's daily token cap.

9.3 Confidence distribution across real runs

Five genuine research runs against live web sources. The spread is the point: a system that returns a high score for every question is not measuring anything.

The 18% run is the most informative result in this report. Asked how much electricity data centres use worldwide, the system gathered 24 sources, supported one claim of five, corroborated none independently, and reported: "4 claims had no supporting evidence in the sources found" and "agreement with the documents the answer was written from is weaker evidence." Data-centre energy figures are widely cited second-hand and poorly sourced. A system that returned 85% here would be worse, not better.

Chapter Ten

Evaluation, Limitations and Future Work

10.1 Defects found and corrected

A structured review of the codebase found a consistent pattern: several controls were documented in comments and marketing copy but did not exist in the running system. These are recorded because the pattern is more instructive than any individual bug.

DefectWhy it matteredResolution
Row-level security absentExtensively documented as "real defense-in-depth"; zero policies existed and both connection strings named the same role.Policies written, second role created, four checks gated in CI.
Circular verificationClaims checked against the text they were summarised from; the score measured fidelity, not support.Independent per-claim search and corroboration flag.
Evidence truncationVerification saw roughly six of forty sources, making most claims unverifiable in principle.Relevance-based selection across all sources.
CI ran on SQLiteThe application refuses to start on SQLite; the green check covered none of the production data paths.Postgres + pgvector service container.
CI had never executedThe workflow file sat one directory below the repository root, where GitHub Actions does not look.Relocated; first successful run followed.
Tables unrenderedEvery Markdown table arrived as a wall of pipes — react-markdown has no table support without a plugin.remark-gfm added; charts and diagrams followed.
Uploads unsanitisedScraped pages were filtered; uploaded documents — far easier for an attacker to control — were not.Sanitised at ingest; context delimited structurally.

10.2 Current limitations

  • The confidence score is unvalidated against human judgement. A harness exists to measure whether "verified" correlates with "true", but it requires human labels that have not yet been collected. This is the single largest gap in the project's evidence.
  • The benchmark corpus is small. Thirty-one paragraphs; recall should be expected to fall on a realistic corpus.
  • Refusal rate is not reliably measured pending a corrected re-run.
  • Ingestion runs in the web process. A restart mid-upload strands a record, mitigated by a reaper rather than solved by a durable queue.
  • Ranking quality is unmeasured beyond MRR; NDCG is not computed.
  • RAG citations are not validated the way research-path citations are.

10.3 Future work, in priority order

  1. Collect human labels for 100+ verified claims and report precision, recall and calibration. Nothing else changes the project's credibility as much.
  2. Expand the benchmark to 200+ questions over a larger corpus, and track scores across runs so regressions are visible.
  3. Validate RAG citations against retrieved chunks, as the research path already does.
  4. Durable job queue for ingestion.
  5. Cross-encoder reranking on the fused candidate set.

10.4 Assessment

The system does what it claims within the limits of what has been measured. Its retrieval is strong on a public benchmark; its refusal behaviour is correct on the cases examined; its confidence scoring is conservative by construction and reports its own reasoning. Its security controls are enforced by the database and verified by the build.

What remains unproven is whether the confidence number corresponds to truth. Every metric in Chapter 9 measures internal consistency or retrieval accuracy. None measures whether a claim marked verified is actually correct — and until human labels exist, that question is open. This report states that plainly rather than letting a column of 1.000 scores imply otherwise.
